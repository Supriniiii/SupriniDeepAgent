# Purpose

The Action Executor performs single discrete actions — the most atomic unit of work in the execution hierarchy. An action is a single tool call, API invocation, file operation, or computation that completes in one step without internal sequencing. The Action Executor provides a uniform interface for invoking any registered action type while handling invocation details, error wrapping, and result normalization.

---

# Responsibilities

- Receive a single action request with parameters
- Resolve the action to its concrete implementation (tool, API, function)
- Validate action parameters before invocation
- Execute the action with appropriate timeout and resource guards
- Normalize the action result into a standard response format
- Wrap and classify errors from the underlying implementation
- Record action execution telemetry
- Support idempotent action replay for retry scenarios

---

# Scope

This component covers the invocation of a single discrete action. It handles parameter validation, invocation, result normalization, and error wrapping. It does NOT sequence multiple actions, manage workflows, or make decisions about what to execute next. It is the lowest execution primitive, invoked by Task Executor or Workflow Executor when they need a single operation performed.

# State Management

The Action Executor is effectively stateless. Each action invocation is independent and self-contained. The only persistent element is the optional idempotency cache which maps idempotency keys to prior results. No execution state is maintained between invocations.

---

# Error Handling

- Parameter validation failure: Return immediately with validation error, no invocation attempted
- Action implementation not found: Return binding error with action type details
- Invocation timeout: Cancel action, return timeout error
- Implementation exception: Wrap in standard error envelope with classification (transient, permanent, unknown)
- Idempotency conflict: Return cached result from prior invocation
- Result normalization failure: Return raw result with normalization warning

# Validation Requirements

- Action parameters must conform to the action type schema
- Action type must resolve to exactly one registered implementation
- Result must be normalizable to the standard response format
- Invocation must complete within timeout bounds
- Idempotent actions must return consistent results for the same key

---

# Extension Points

- Custom action type registrations
- Pluggable result normalizers per action category
- Custom error classification rules
- Action invocation middleware (logging, auth, rate limiting)
