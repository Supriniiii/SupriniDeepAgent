# Purpose

The Self-Review component examines the agent's own outputs before they are delivered to consumers. It acts as an internal quality gate that reviews generated artifacts (code, documents, plans, configurations) for correctness, completeness, consistency, and adherence to standards. It catches errors that execution alone cannot detect by applying critical reasoning to the agent's own work.

---

# Responsibilities

- Receive generated outputs before final delivery
- Review outputs for logical correctness and internal consistency
- Check adherence to defined standards and conventions
- Identify gaps, omissions, or incomplete sections
- Detect contradictions between output sections
- Verify that outputs satisfy the original request requirements
- Produce review findings with severity classifications
- Recommend specific corrections for identified issues

---

# Scope

This component covers pre-delivery quality review of the agent's own outputs. It applies critical reasoning to detect issues that automated validation cannot catch. It does NOT modify outputs directly (corrections are recommendations), execute tasks, or perform post-execution analysis across multiple runs. It operates as a single-pass review gate before output delivery.

# State Management

The Self-Review component is stateless across review cycles. Each review operates independently on the provided output and standards. Review findings are emitted and not retained internally. If iterative review is needed (output revised and re-reviewed), the revised output is submitted as a new review request.

---

# Error Handling

- Unreadable output: Report as critical finding, reject output
- Missing quality standards: Apply built-in default review criteria, flag standards absence
- Review timeout: Emit partial findings reviewed so far, flag incomplete review
- Schema validation failure: Include as high-severity structural finding
- Conflicting standards: Apply strictest interpretation, note conflict in findings

# Validation Requirements

- Every finding must have a severity level and specific location in the output
- Rejection decisions must cite at least one critical or multiple high-severity findings
- Approval decisions must confirm all critical checks passed
- Correction recommendations must be specific enough to act upon
- Review must cover all sections of the output (no silent skips)

---

# Extension Points

- Custom review criteria per output type (code, documentation, configuration)
- Pluggable domain-specific review rules

- Integration with external code review or linting tools
